# تحديث v0.6 — التشغيل عبر Socket Mode بدون رابط HTTPS عام

أُضيف نمط Socket Mode كبديل تجريبي لخادم callback العام. الكود يدعم الوضعين؛ **الوضع القديم HTTP يظل موجودًا** ولم يتم النشر أو الاتصال بأي مشروع إنتاجي.

**الفائدة:** تختفي عقبة إعداد 3 روابط HTTPS داخل Slack، لكن تظل هناك حاجة إلى تشغيل عملية Node.js مستمرة، وبيئة Firebase Emulator منفصلة، وتهيئة App-Level Token بصلاحية `connections:write` وBot OAuth Token من صفحة Slack App. يُرجى حفظ الرموز في مدير أسرار وليس في المحادثات.

**ملفات الوضع الجديد:** `app-manifest.socket-mode.yaml` + `.env.socket-mode.example`.

**داخل Slack API:** افتح التطبيق الحالي الذي يبدأ اسمه بـPark، وتأكد من أنه التطبيق الصحيح بدل إنشاء آخر. فعّل Socket Mode من إعداداته وولّد App-Level Token بصلاحية `connections:write`، ثم راجع App Home وInteractivity وSlash Commands وصلاحيات OAuth المحددة بالـmanifest. قد يلزم إعادة تثبيت التطبيق بعد تغيير الأذونات. **هذه الخطوات لم تُنفّذ تلقائيًا** لعدم وجود صلاحية تعديل Slack Apps من اتصال المحادثة.

**التشغيل الآمن:** شغّل Firebase Emulator محليًا بمشروع وهمي `snag-ops-staging`، ثم خزّن الرموز في بيئة تشغيل خاصة وعين `SLACK_SOCKET_MODE=true`. نفّذ `npm test`, `npm run check`, و`npm run doctor`، وبعدها `npm start`. لا يبدأ هذا المسار من Firebase الإنتاجي ولا يحتاج عنوان HTTPS عام. لا تشارك بيانات فعلية.

**ما يزال غير مكتمل:** تثبيت إعدادات التطبيق من Slack API، تشغيل الخادم/المحاكي، واختبار End-to-End الحقيقي. نجاح الاختبارات البرمجية وحده لا يثبت ذلك.

## تحديث v0.5 — جاهزية التثبيت بدون ادعاء النشر

أُضيف فحص مستقل بالأمر `npm run doctor` يراجع هوية Workspace، وقائمة المستخدمين المسموح لهم، وعزل Firebase، وعناوين Slack الثلاثة في Manifest، بدون إجراء طلبات شبكة أو إظهار Bot Token أو Signing Secret.

المشروع **لا يصبح مثبتًا وقابلًا للتشغيل** إلا بعد تعديل عناوين `STAGING_HOST.example.com` في Manifest إلى خادم حقيقي، وتوفير بيانات OAuth وأسرار Slack في بيئة آمنة، وتشغيل قاعدة Staging منفصلة. يجب أن تكون نتيجة `npm run doctor` كلها PASS. الاختبارات المحلية لا تمثل اختبارًا متكاملًا على حساب Slack الفعلي.

أُضيف كذلك تحقق من عدم الإسناد إلى أي مستخدم Slack خارج قائمة السماح أثناء التجربة.

**GitHub:** طلب تعديل الإشعارات [PR #2](https://github.com/ahmedsaad6540-stack/snag-app-firebase/pull/2) مستقل عن مشروع Slack هذا، وهو Draft لم يُدمج. حاول المساعد نقله إلى Ready وإجراء Merge لكن اتصال GitHub رفض الطلبين بـ`403 Resource not accessible by integration`. لا تدّعي أنه مُدمج.

## الملفات المهمة

- `app-manifest.yaml`: ملف تعريف Slack App وOAuth Scopes.
- `src/app.js`: بوت Slack باستخدام Bolt وApp Home.
- `src/views.js`: أوامر العمل؛ النماذج ودورة الحالات.
- `src/catalog.js`: كل بنود Park Street 51.
- `src/restroomCatalog.js`: 50 حمامًا و29 مكوّنًا.
- `src/operationsViews.js`: الشاشات التفاعلية للأقسام الأخرى.
- `src/operationsRepo.js`: قراءة/كتابة Backend إلى Staging فقط.
- `src/config.js`: منع `snag-app-firebase` مهما كانت البيئة.
- `firebase-staging.rules`: قواعد Firestore للبيئة التجريبية، تمنع أي وصول Web/Mobile؛ العمليات تتم عبر Admin SDK فقط.
- `preview/Park_Street_Operations_Interactive_Demo.html`: تجربة مستقلة تفتح بدون شبكة.
- `test/`: اختبارات العقد والبيانات والأمان.

## تجربة بدون اتصال أو دفع

1. افتح `preview/Park_Street_Operations_Interactive_Demo.html` في أي متصفح.
2. انتقل بين الأقسام؛ أضف بلاغًا وهميًا، سجل بند تفتيش، غيّر حالة عمل، أو أدخل تعداد حمام؛ يمكن التصدير إلى CSV.
3. هذه الصفحة لا تتصل بـSlack أو Firebase. البيانات موجودة داخل LocalStorage بمتصفحك فقط.

## تثبيت Slack App — عندما تصبح صلاحية إنشاء التطبيق متاحة

1. افتح `https://api.slack.com/apps` واضغط Create New App → From manifest، ثم استورد `app-manifest.yaml` بعد تعديل `STAGING_HOST.example.com` إلى خادم HTTPS تجريبي.
2. ثبّت التطبيق في Workspace الاختباري، لكن لا تدعُ موظفين أو تنشر رسائل بيانات حقيقية.
3. خذ Bot OAuth Token وSigning Secret واحفظهما في **Secret Manager/بيئة الخادم** — لا تضعهما في Git أو داخل أي رسالة.
4. استخدم Staging Firebase **مشروعًا منفصلًا** من نوع `*-staging` أو Firestore Emulator محليًا؛ ممنوع استخدام `snag-app-firebase` الحالي.
5. في بيئة التطوير المحلية، انسخ `.env.example` إلى ملف خاص خارج Git ثم أضف القيم الحقيقية. مثال متغيرات:

   ```env
   FIREBASE_PROJECT_ID=snag-ops-staging
   FIRESTORE_EMULATOR_HOST=127.0.0.1:8080
   SLACK_ALLOWED_TEAM_ID=T<workspace_id>
   SLACK_ALLOWED_USER_IDS=U0CAL6BQX38
   SLACK_ENABLE_FILE_UPLOAD=false
   ```

6. نفذ `npm install` ثم `npm test` ثم `npm start` بعد تشغيل Firestore Emulator والخادم العام التجريبي. يحتاج Slack مسار Webhook عام HTTPS صالحًا في `https://.../slack/events`.
7. تأكد من ظهور App Home ونموذج البلاغ التجريبي واستجابة التحديثات وقائمة فحص الحمامات.
8. بعدها فقط فكر في تنشيط الصور والسجلات الحقيقية بعد مراجعة وتهيئة قواعد Firestore الإنتاجية وتعيين أذونات الموظفين. لا تفعّل فوترة Firebase Blaze تلقائيًا.

> **تنبيه:** Token / Signing Secret / Service Account لا ينبغي كتابتها في Slack أو GitHub أو مستند عام. حتى لو وصف GitHub الحساب بأنه يملك صلاحية `push`، فإن واجهة الاتصال الحالية أعادت `403` عند محاولة إنشاء فرع؛ لذلك لم نرفع الكود إلى GitHub.

## مراجعة أمان الإنتاج

تمت مراجعة ملف `snag-app/firestore.rules` في GitHub الرئيسي ووُجدت قاعدة `allow read, write: if true`. **هذا خطر إذا كانت القاعدة منشورة فعلاً**؛ لا نملك فحص القواعد الحية من اتصال Firebase المتاح في هذه المحادثة. يجب التحقق من قواعد Firebase Console والعمل على نسخة اختبار قبل نشر قواعد تقييد الوصول، لأن تسجيل المستخدمين وبعض وحدات التطبيق الحالي تتوقع سلوكًا محددًا للصلاحيات.

## قيود مؤكدة في هذه الجلسة

- لا توجد أداة Firebase متاحة هنا للنشر أو فحص Security Rules المنشورة.
- لم نستطع إنشاء فرع في GitHub باستخدام الاتصال الحالي بسبب الخطأ `403 Resource not accessible by integration`.
- لم يتوفر اتصال إدارة/إنشاء Slack Apps من أدوات Slack المثبتة في الجلسة، وإن كان يمكن إرسال رسائل وقراءة قنوات؛ لذا لا يصح ادعاء ظهور التطبيق الجديد داخل Slack حتى يتم استيراد Manifest وتشغيل الخادم.
- اختبارات Node الموجودة في الحزمة تفحص الدوال وبنية Slack وعمليات العزل ببيانات اصطناعية؛ ولا تدّعي نجاح اختبار E2E مع Slack وFirebase حقيقيين.

## خطة استكمال التطابق الوظيفي

1. نقل حقول الوحدات والمخازن والقوائم من Components الأصلية 1:1، مع استخدام متغيرات الاختبار فقط.
2. دعم بيانات الصور ومراجعة التكاليف وعمليات الإسناد والتعليقات وموافقات الفحص.
3. استكمال وحدات AI والتقارير التصديرية والجولات التاريخية؛ تختبر داخل Firebase Emulator.
4. إجراء اختبارات أمن وتكامل وفحص صلاحيات المستخدمين ثم تهيئة بيئة Staging عامة.
5. بعد الاختبار ومراجعة القواعد المنشورة، فقط يتم ربط المشروع الإنتاجي **بموافقة نشر محددة**.
